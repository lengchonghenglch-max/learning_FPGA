# linetest 学习记录

## 1. 功能理解

### 它是什么？

`linetest` 是一个基于 UART 的“整行回显”测试顶层。

它做的事情不是“收到 1 个字节立刻发回”，而是：

1. 用 UART RX 接收串口输入的数据。
2. 把接收到的字节先存进内部缓冲区。
3. 等收到“换行/回车”，或者一行长度超过 80 字节后，再启动 UART TX。
4. 把这一整行数据按顺序发送回去。

可以和 `echotest` 做一个直接对比：

```text
echotest : RX -> TX
linetest : RX -> buffer[head/tail] -> TX
```

`echotest` 是单字节即时回显，收到一个字节后就尽快发回一个字节。  
`linetest` 是缓存后整行回显，先把字节写进内部缓冲区，再在满足行结束条件后统一发送。

### 为什么要这样设计？

`echotest` 只能验证“单字符收发链路基本通了”，而 `linetest` 更接近真实通信场景，因为它同时验证：

- UART 接收是否正确
- 缓冲区/FIFO 思想是否正确
- UART 发送是否正确
- 读写指针配合是否正确
- 一整行数据的边界控制是否正确

### 怎么工作？

下面是它的主数据流：

```text
UART RX --> rxuart --> rx_data/rx_stb --> buffer[head]
                                         |
                                         v
                              lineend / run_tx 控制
                                         |
                                         v
                               buffer[tail] --> txuart --> UART TX
```

### 最小例子

假设串口输入：

```text
H e l l o \r
```

则模块行为是：

1. `H e l l o \r` 依次被 RX 接收。
2. 每收到 1 个字节，就写入 `buffer[head]`。
3. 收到 `\r` 后，`run_tx` 置 1。
4. TX 从 `tail` 指向的位置开始，把这一行重新发出去。

## 2. 核心状态机 / 逻辑分析

`linetest` 没有写成显式 `case` 状态机，但它本质上有 3 段控制逻辑：

### 2.1 接收写缓冲

- `rx_stb` 表示“收到 1 个有效字节”
- `buffer[head] <= rx_data` 每拍都在写当前地址
- 只有满足以下条件时，`head` 才前进：
  - `rx_stb == 1`
  - 不是 `break`
  - 没有奇偶校验错误 `rx_perr`
  - 没有帧错误 `rx_ferr`
  - `nxt_head != tail`，避免写满覆盖

可以把它理解成：

```text
收到合法字符 --> 写入 buffer --> head 前进
收到错误字符/缓冲区满 --> 丢弃，不推进 head
```

### 2.2 发送启动条件

`run_tx` 是整个“开始发一整行”的关键控制信号。

启动条件有两个：

1. 收到换行 `0x0A` 或回车 `0x0D`
2. 当前缓存字符数 `nused > 80`

停止条件：

1. `tail == lineend`

这表示：

```text
先积累一行 --> 行结束 --> 启动发送 --> 发到 lineend 为止 --> 停止
```

例如输入：

```text
A B C D \r
```

那么 `run_tx` 不会在收到 `A/B/C/D` 时拉高，而是在收到 `\r` 的那一拍拉高。

原因是 `\r` 或 `\n` 在这里就是“这一行结束”的触发条件。

`run_tx` 拉高以后，模块不会立刻停止接收新的 UART 字节。

原因是接收路径和发送路径是并行、独立工作的：

- `head` 负责写入缓冲区
- `tail` 负责从缓冲区读出并发送
- `rxuart` 并不会因为 `run_tx = 1` 就被关闭

所以系统可以一边发送当前这一行，一边继续接收后续新字节。

这里只要区分清楚两个边界就行：

```text
head    管“新数据写到哪里”
tail    管“当前这一行发到哪里”
lineend 管“这一轮发送到哪里为止”
```

发送是否真的能继续推进，还要满足发送握手：

1. `tx_stb = 1`，表示当前拍提出发送请求
2. `tx_busy = 0`，表示发送器当前空闲、可以接收该字节

因此，`run_tx = 1` 只表示“允许进入发送阶段”，并不表示“停止接收”。

这里 `lineend` 必须单独保存，原因是：

- `head` 是写指针，后续还可能继续变化
- 模块在发送当前这一行时，仍然可能继续接收后面的新字节
- 因此不能直接拿“当前的 `head`”当作发送终点

`lineend` 的作用就是在“行结束触发”的那一拍，把本次要发送的边界锁存下来。

可以把它理解成：

```text
head    = 现在已经写到哪里
lineend = 这一轮发送最多发到哪里
```

所以，`lineend` 的核心作用不是防止写溢出。
防止写满覆盖的主要机制是：

```text
nxt_head != tail
```

而 `lineend` 解决的是另一个问题：

```text
TX 到底什么时候该停
```

当收到回车或换行时，代码里常写：

```verilog
lineend <= head + 8'h1;
```

而不是：

```verilog
lineend <= head;
```

原因是当前这个“结束字符”本身也属于这一行数据。

在触发行结束的这一拍：

- 当前字节已经对应到 `buffer[head]` 这个写入位置
- `head` 代表的是“当前写地址”
- 如果直接写 `lineend <= head`，发送边界就会少包含 1 个字节

所以这里用 `head + 1`，本质上是在说：

```text
这一行的最后一个有效字节已经占用了当前 head 位置
发送终点应该落在“下一个位置之前”
```

也可以直观理解为：

```text
如果第一个字节写在 buffer[0]
那么写完第 8 个字节后，结束边界应该对应“8”，而不是“7”
```

### 2.3 发送读缓冲

- `tx_data <= buffer[tail]`
- `tx_stb <= run_tx`
- 当 `tx_stb && !tx_busy` 时，说明发送器接受了这个字节，此时 `tail` 前进

关键点是：

`tail` 不是“每拍都加 1”，而是“发送器真正接收了这个字节”才加 1。

这能避免发送器忙的时候跳读数据。

更准确地说：

- `run_tx = 1` 只表示“系统希望继续发送”
- `tx_stb = 1` 表示“当前拍提出发送请求”
- `tx_busy = 0` 表示“发送器当前能接收这个字节”

只有在：

```text
tx_stb && !tx_busy
```

这一拍成立时，才能说明“`buffer[tail]` 这个字节已经被发送器接收走了”。

因此 `tail` 的含义不是：

```text
准备发送到哪里
```

而是更接近：

```text
已经成功交给发送器的数据边界在哪里
```

如果 `tail` 在 `run_tx = 1` 之后每拍都自增，那么当发送器仍然忙时，就会出现：

1. 后续字节被提前跳过
2. 某些字节根本没有被发送器接收
3. 最终造成丢字节或发送顺序错误

所以这里本质上是一个“握手成功再移动指针”的设计。

## 3. 关键知识点总结

### 3.1 这不是严格意义上的独立 FIFO 模块

这里用了 FIFO 思想：

- `buffer`
- `head`
- `tail`

但它不是单独封装的 `ufifo.v`，而是在 `linetest` 里手写了一个简化的环形缓冲。

### 3.2 `head - tail` 可以表示已用深度

```text
nused = head - tail
```

因为 `head` 和 `tail` 都是 8 位，天然会回绕，所以这个写法在环形缓冲里是成立的。

### 3.3 为什么要判断 `nxt_head != tail`

这是防止缓冲区写满时覆盖未发送的数据。

如果继续写，就会把还没来得及发送的数据冲掉，导致整行回显错误。

建议重点看两个波形阶段：

1. 接收阶段：`rx_stb` 拉高时，`head` 是否前进
2. 发送阶段：`run_tx` 拉高后，`tail` 是否只在 `!tx_busy` 时前进

如果只选最少 4 个信号来证明“先收一整行，再开始发送”，推荐优先看下面这组：

1. `rx_stb`
作用：证明接收器已经成功收到一个字节。相比直接看 `i_uart_rx` 串行波形，`rx_stb` 更容易判断“字节级接收事件”。

2. `head`
作用：证明接收的数据已经真正写入缓冲区。`head` 前进说明 line buffer 正在累计一整行，而不是边收边立刻发。

3. `tx_stb`
作用：证明系统已经开始向发送器提出“发送请求”。它能直接体现“什么时候从接收阶段切换到发送阶段”。

4. `tx_busy`
作用：证明发送器是否接受并处理发送请求。结合 `tx_stb` 可以判断发送握手是否成立，也能解释为什么 `tail` 不能随便前进。

如果想再补一个最直观的外部结果信号，再加：

5. `o_uart_tx`
作用：直接观察串口输出线何时真正开始往外发送。

为什么这里更推荐看 `rx_stb`，而不是直接看 `i_uart_rx`：

- `i_uart_rx` 是串口输入线上实时变化的电平，只能直接反映比特级波形变化
- 它会随着起始位、数据位、停止位不断翻转，信息很多，但不容易直接判断“一个完整字节何时接收完成”
- `rx_stb` 则是字节级完成标志，它拉高时表示接收器已经完成了当前字节的判定与输出

因此：

```text
i_uart_rx 适合看底层串行位波形
rx_stb    适合看上层字节接收流程
```

而当前 `linetest` 的目标是验证“先收一整行，再开始发送”的字节级流程，所以 `rx_stb` 更直接。

## 5. Debug / 遇到的问题

### 当前已知值得反思的问题

1. `buffer[head] <= rx_data` 是每拍都在执行，为什么不会把错误数据真的“写坏”？
2. `lineend <= head + 1` 为什么不是直接等于 `head`？
3. `tx_stb <= run_tx` 为什么能连续驱动发送，而不是只打一拍？

### 当前结论

`linetest` 的核心不是复杂状态机，而是：

- UART RX 接收字节
- 环形缓冲暂存字节
- 以“换行/超长”为边界启动发送
- UART TX 顺序发回整行
